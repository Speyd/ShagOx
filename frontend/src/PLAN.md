# ShagOx (Marketly) — стан проєкту

Оновлено: 20.11.2026

## Коротко

«База» для маркетплейсу є: можна зареєструватися, виставити товар, знайти його в каталозі,
відкрити сторінку, додати в кошик чи обране, порівняти, залишити відгук і керувати своїми
товарами в профілі. Є адмінка для всіх довідників і сутностей.

Основний сценарій покупки тепер закритий: кошик → оформлення (самовивіз або Нова Пошта з розрахунком
доставки) → сторінка «Дякуємо» → список замовлень у профілі. Залишились другорядні сторінки-заглушки
і кілька знайдених багів (див. нижче).

Збірка: `npm run build` проходить, `npm run lint` — 0 помилок, бекенд збирається.

## Що є лише частково / заглушки

| Що | Стан | Що треба |
|---|---|---|
| Відстеження замовлення | Статична сторінка, кнопка «Знайти» нічого не робить | Пошук за номером замовлення (`OrderNumber`) |
| Сповіщення | Усі вкладки показують «Немає нових сповіщень» | Можна прибрати з меню або лишити як «у розробці» |
| Вибір категорій (онбординг) | Зберігається в браузері, але ніде не використовується | Або використати на головній, або прибрати |

## Виправлено в цій сесії

**20.11.2026**

- Повний цикл замовлення: підтвердження продавцем, відправка (ТТН, посилання на відстеження НП), завершення, скасування / відхилення з поверненням залишку; вкладка «Продажі».
- Онлайн-оплата: статус і таймер на сторінці замовлення, повторна оплата протягом 3 днів (з повторним резервуванням товару), автоповернення коштів при відхиленні оплаченого і при запізнілій оплаті.
- **Безпека:** вебхук Monobank не перевіряв підпис — будь-хто міг позначити замовлення оплаченим. Додано перевірку X-Sign.
- Воркер прострочення оплати не спрацьовував для неоплачених рахунків і впав би на першому; посилання в банку жило 24 год замість 20 хв.
- Кеш замовлення не скидався після оплати; `paidAt` не заповнювався.
- Продаж понад залишок при одночасних покупках (результат списання не перевірявся).
- Оформлення з оплатою при отриманні падало з 400 (фронт слав `OnDelivery`, бекенд чекає `CashOnDelivery`).
- Перевірено через API наскрізним сценарієм (78 перевірок, включно з гонками), тестові дані прибрано.

**19.11.2026**

- dev.dmarketly.com давав 502: Vite слухав лише `[::1]`, тунель Cloudflare ходить на `127.0.0.1`.
- Вхід через форму падав: БД не мала 6 міграцій (`column c.Ccy does not exist`). Міграції застосовано.
- Реєстрація падала з `IX_Cities_Code`: місто Київ (і тип товару) мали `Id = 0` після імпорту дампу →
  EF вставляв їх повторно. Виправлено скриптом `backend/scripts/fix-zero-ids.sql`.
- Після реєстрації через форму на Google-акаунт вхід просив код, а підтвердження казало «вже підтверджено».
- Видалення з кошика падало («Не вдалося видалити атрибут позиції»): `Update()` репліко-сутності ламав трекер EF.
- Форми входу, реєстрації, відновлення і зміни пароля використовують спільні поля та одну форму коду.
- Адмін-категорії: фронт слав JSON на `multipart`-ендпоінт (нічого не зберігалось), фото було обовʼязковим, перевірки при створенні ігнорувались, видалення падало без фото, оновлення/видалення чіпляли до основної БД граф з репліки з усіма оголошеннями категорії. Додано поле «Зображення» в адмін-форму.

**15.11.2026**

- **Додавання товару не працювало взагалі.** Варіанти створювались у транзакції, а оголошення
  перевірялось через репліку БД, яка ще не бачила незакомічений запис → «Оголошення не знайдено».
- **Стан товару англійською.** У таблицях перекладів (стани, статуси, міста, регіони) статус був
  записаний як `'0'` замість `'Active'` → API не знаходило переклад. Виправлено в БД і в сід-скрипті;
  фронт тепер завжди просить українську.
- **Редагування товару губило зміни.** Ціна не зберігалась (регістр полів), фото ігнорувались
  (`images` замість `Pictures`), атрибути товару затирались, синхронізація фото падала.
- **Фото у відгуку не можна було прибрати.** Форма редагування не показувала фото, бекенд приймав
  JSON (файли не передати) і пропускав синхронізацію фото, якщо текст не змінився.
- **Безпека:** можна було змінити ціну чужого варіанта через своє оголошення.
- Новий товар не зʼявлявся в «Моїх товарах» до години (кеш); список тепер від нових до старих.
- `GET /advertisements/short-search` падав з 500.
- `npm run build` не збирався (8 помилок TypeScript); видалено 3 мертві дублікати адмін-сторінок.
- Биті посилання: «Додати оголошення» з порожньої категорії, текст «немає обраних товарів» у замовленнях.

## Відомі проблеми / технічний борг

- **Читання з репліки під час запису.** Частина сервісів читає сутність з репліки, а потім змінює
  її в основній БД. Для товарів, фото і відгуків виправлено; інші місця з тим самим шаблоном
  (кошик, профіль, адмін-оновлення) варто перевірити, якщо щось «не зберігається».
- `Repository.Update` ковтає винятки й повертає `false` — помилки збереження можуть бути непомітні.
- Кеш Redis живе 1 год: після ручних змін у БД дані на сайті оновлюються не одразу.
- `GET /api/users/contact/{contact}` без авторизації віддає профіль користувача (Id, валюта, lastSeenAt) — ризик приватності.
- `POST /api/baskets` для наявного кошика повертає 400, а фронт чекає 409 (зараз не заважає: кошик створюється при реєстрації).
- Gmail SMTP блокується в мережі URAN; у Development код підтвердження пишеться в лог бекенду.
- Підтверджене продавцем, але не відправлене замовлення ніхто не нагадує відправити; непідтверджені замовлення не скасовуються автоматично.
- Якщо автоповернення коштів не вдалося (банк відмовив), це лише пишеться в лог — потрібна ручна обробка.
- Опис типів товарів у БД — російською (на сайті не показується).
- Тестів немає ні на фронті, ні на бекенді.
- Залежності з відомими вразливостями: `Newtonsoft.Json 9.0.1`, `Microsoft.AspNetCore.WebUtilities 2.3.9`.
- Бандл фронта > 500 КБ (немає code-splitting для основних сторінок).
- `README.md` описує проєкт дуже загально.
